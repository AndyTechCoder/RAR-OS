# Signed runtime campaign — source candidate

This integrates M4.2 native progress correlation and the disposable cloud test.
It is not an acceptance report, not M4.3, and never runs on the owner Mac/SSD.

## Native correlation

REPORT codes 16–20 require the existing Manager capability and zero extra
arguments, and emit fixed request/rejected/installed/fallback/active-lost labels.
They are correlation hints, not independent proof. Installation reports only
after durable publication, exact authenticated incarnation binding and physical
retirement. A Settings UD2 label is derived from the kernel's active Settings
binding and real vector 6 trap, not an application-supplied success claim.
The one-shot laboratory request and one fresh-prior fallback remain unchanged.

## Actual campaign

The trusted-main manual workflow accepts one exact reviewed source SHA. It
reuses the existing inspected nonroot, networkless, read-only-root container
profile, inherited private NBD sockets, fixed synthetic geometry, firmware,
QMP preflight and bounded deadlines. It compiles both compositions twice,
signs only public laboratory fixtures, checks exact reproduction and immutable
bank placement, and packages the actual signed kernel. No source helper becomes
controller authority. No existing image is formatted, reset or deleted.

Each of four literal cases owns fresh cloud fixtures and three fresh VMs:
1. Boot factory, create a random challenge file through actual Terminal, join
   all processes and freeze authenticated Data.
2. Retain the same images, make Data physically read-only, issue the fixed
   update/bad-health/bad-signature/bad-ABI command. Observe actual Settings pixels
   and a saved file. For the valid update, change spacing, induce the private
   laboratory Settings fault and observe fresh verified factory fallback.
3. Boot the exact retained disks, observe factory Settings and the file. After
   valid update/fallback, also reject stale generation 2 without System writes.

System writes are allowed in the auditor only by explicit boolean mode on the
second VM's System role. Legacy scenarios retain the default no-write rule.
Each cut requires whole-VM/three-backend joins, audited durable flushes, exact
three separate retained inode identities and drained QMP. Data is compared
byte-for-byte; the System selector/slot result and all accepted full frames are
independently reconstructed. Fixed input and lifecycle ordering are checked.

## Limits and acceptance

The public RFC laboratory signer is not a production key or Secure Enclave.
Twelve VM observations are bounded to four 600-second containers, not a retry
loop. Each VM retains the existing 120-second limit. Failure stops the campaign.
Artifacts are retained remotely with exact source/controller/image provenance.
The independent checker rejects malformed evidence but source self-tests do not
prove guest behavior. Its result explicitly leaves provenance and milestone
acceptance false; review of the actual trusted workflow/run is still required.
M4.2 remains incomplete until real signed runtime evidence and remaining
acceptance requirements pass. M4.3 recovery is not implemented by this change.

# Mounted-error scenario candidate

Not activated and not runtime acceptance. Uses the existing fixed Modern cloud profile, fresh public Data fixture and first WRITE/error injection. After the exact planned error, keep the same VM alive; observe Terminal Unavailable, then typed LIST, locked WRITE and LIST completion, followed by Files Unavailable. Each typed-command frame precedes Enter. No post-error backend request is allowed, including rejected retries or remount reads. Join the whole VM and all three backends before requiring unchanged Data/System/boot bytes.

This closes a different gap from corrupt-header mount rejection: a successfully mounted service must become sticky-failed after publication I/O failure. The candidate adds no device, path, syscall, capability, networking or launch option. This change includes the fixed launcher entry, independent retained-envelope validator and dedicated trusted-main workflow/controller mode. It is not dispatched or accepted until independent review and exact-head source checks pass and the controller is merged. The dedicated mode reuses two independent builds but does not repeat the already-successful persistence/corrupt-mount campaign. Inert scenario tests alone are not guest proof. Existing successful persistence/crypto evidence must not be rerun merely to document this candidate.
